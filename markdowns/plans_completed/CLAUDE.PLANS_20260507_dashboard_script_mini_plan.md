# Mini-plan: joplin-mcp dashboard script (config-driven Joplin → Markdown table generator)

_Status: draft. Records the agreed scope after one /framing cycle on the use case and one /framing + /research cycle on the backend choice (see `research_output/2026-05-06_joplin-backend-decision.md` in this repo)._

## Backend decision (recommended, pending user confirmation)

**REST API for v1 via the existing joplin-mcp client (`client.search_all`), with a pluggable `Loader` interface from day one. SQLite implementation deferred to v1.5 with explicit triggers.**

Key research finding that drives this: Joplin's `/search` endpoint **does** support combined-criteria queries server-side, including `any:1 tag:A tag:B notebook:X notebook:Y` returning `(A∪B)∩(X∪Y)` correctly. Verified against Joplin source (`queryBuilder.ts`, `filterParser.ts`) AND empirically against the live Joplin Desktop REST API on 2026-05-06 (full matrix in `research_output/2026-05-06_joplin-backend-decision.md`). The previous capability audit's claim that "client-side intersection is required" was wrong; corrected here. The single structural limit remaining is no per-clause grouping (e.g., `(A AND B) OR (C AND D)` not expressible) — not relevant for v1.

Secondary findings:
- E2EE encrypts only at sync serialization; the local SQLite stays plaintext at rest including bodies, so future E2EE adoption does NOT force REST. SQLite remains a viable v1.5 path.
- Joplin SQLite schema has been additive-only for the last 18 months (migrations 42–49); the columns relevant to dashboard queries (`notes.id|title|body|parent_id|updated_time`, plus `tags`/`note_tags`/`folders`) are stable.
- Known REST caveats: `/search` index can lag after sync ([joplin#11631](https://github.com/laurent22/joplin/issues/11631)) and free-text-with-filter combos break with OCR text ([joplin#12128](https://github.com/laurent22/joplin/issues/12128)). Triggers to add the SQLite loader if these bite.

Triggers to add the SQLite loader:
1. Sync staleness biting real workflow (a dashboard refresh routinely shows stale state right after capture/edit)
2. OCR-text edge case affecting a real query
3. A use case requiring the dashboard to run when Joplin Desktop is not open

## Context

Multiple GTD-style use cases share the same need: query Joplin notes filtered by notebook(s) and tag(s), render the results as a Markdown table or grouped list, write the output to a file. First consumer is the `job_search` project; future consumers may include other GTD aggregations where the table IS the answer (no priority triage required).

The user explicitly excluded `!Projects Registry` from this tool's scope: priority assessment requires user judgment, not aggregation.

## Outcome

A small Python package living in this repo (`joplin-mcp`) that:

- Queries Joplin by notebook + tag filters
- Renders Markdown tables/sections from the results
- Reads a YAML config defining one or more sections per dashboard
- Writes the assembled dashboard to a configured output path
- Exposes both a library API (for direct Python use) and a CLI (`joplin-dashboard <config.yaml>`)

## Library home

`~/projects/dev/joplin-mcp/src/joplin_mcp/dashboard/` (or `~/projects/dev/joplin-mcp/joplin_dashboard/` — exact placement TBD by joplin-mcp project conventions). Reasons:

- joplin-mcp is the natural home for Joplin-tooling code; reusing its dependency setup, test infrastructure, and packaging is "free"
- Keeps the dashboard logic adjacent to the MCP server code that already wraps the Joplin API
- The Joplin client/auth/config code already lives here; no duplication
- Makes promotion/decoupling later mechanical if the dashboard utility outgrows the parent project

## Architecture

### Layers

1. **Query layer.** `query_notes(notebook=..., tags_required=..., tags_excluded=..., search=...) -> list[NoteRecord]`. NoteRecord is a typed dict with `id`, `title`, `body`, `notebook_path`, `tags`, `created_time`, `updated_time`, optional parsed frontmatter dict. Backend is pluggable (REST API today; SQLite later if the next /framing cycle picks that path).

2. **Render layer.** `render_section(notes, columns=..., group_by=..., sort_by=..., sort_dir=...) -> str` produces a Markdown section (header + table or grouped lists). Columns are an ordered list of column specs. Group-by can be a tag prefix (e.g., `Job: Phase`) or a frontmatter field.

3. **Assembly layer.** `assemble_dashboard(sections, header=None, footer=None) -> str` concatenates rendered sections with optional header/footer (typically a generation timestamp).

4. **CLI.** `joplin-dashboard <config.yaml>` — reads the YAML, runs queries, writes the output file. Exit non-zero on errors with informative stderr.

### YAML config schema (sketch)

```yaml
output: ~/projects/dev/job_search/DASHBOARD.md
header: |
  # Job Search Dashboard
  _Auto-generated by joplin-dashboard. Do not hand-edit._
  _Last refreshed: {timestamp}_

sections:
  - title: "People — active"
    notebook: "1-Job Search/People"
    tags_required: ["Job: Status: Active"]
    columns: [title, tags, updated]
    sort_by: updated
    sort_dir: desc

  - title: "Applications by phase"
    notebook: "1-Job Search/Applications"
    tags_excluded: ["Job: Status: Archived"]
    group_by_tag_prefix: "Job: Phase"
    columns: [title, type, updated]
    sort_by: updated
    sort_dir: desc

  - title: "Orgs"
    notebook: "1-Job Search/Orgs"
    columns: [title, status, updated]
    sort_by: title
    sort_dir: asc

  - title: "Positions — active"
    notebook: "1-Job Search/Positions"
    tags_required: ["Job: Status: Active"]
    columns: [title, updated]
    sort_by: updated
    sort_dir: desc
```

### Column spec

Built-in columns: `title`, `tags`, `notebook`, `created`, `updated`, `id`. Frontmatter columns: any YAML key from the parsed frontmatter (e.g., `column: org` reads the `org` field if the note body starts with frontmatter). v1 emits the raw value; later versions can add link resolution.

### Group-by semantics

- `group_by_tag_prefix: "Job: Phase"` — for each note, find its first tag matching the prefix; use the suffix (e.g., `4`) as the group key. Notes with no matching tag go into a `(none)` group.
- `group_by_frontmatter: <field>` — group by the value of the named frontmatter field.
- Groups are emitted as H3 sub-sections under the section H2.

### Loader interface (pluggable)

A thin `Loader` abstraction keeps the backend swappable. Two candidate implementations:

- `JoplinRestLoader` (v1) — uses joplin-mcp's existing `client.search_all(query=...)`. Combined queries (`tag:X notebook:Y`, `-tag:Y`, etc.) are passed through verbatim and resolved server-side per Joplin's queryBuilder; no client-side intersection. Roughly one `/search` call per dashboard section. Caveat: search-index can lag after sync; OCR-text bug exists.
- `JoplinSqliteLoader` (v1.5, deferred) — opens the desktop SQLite read-only. SQL JOINs across `notes`, `note_tags`, `tags`, `folders` in a single query per section. Bypasses sync-index staleness and OCR bugs. Schema verified stable for the relevant columns; E2EE does not encrypt the local file at rest. Triggers to build it: see Backend decision section above.

The Loader interface is small — likely `load_section(notebook_path: str, tags_required: list[str], tags_excluded: list[str], extra_query: str | None) -> list[NoteRecord]` plus an init for any backend-specific config (Joplin token vs. SQLite path). Two implementations of one interface; no backend-specific leakage above the Loader layer.

## Out of scope for v1

- **Cross-reference resolution.** v1 emits raw frontmatter / tag values in columns. Resolving `org: mgb` to a hyperlink to the MGB Joplin note is v2.
- **Push to Joplin** as a `!Job Search Dashboard` note in addition to writing the file. v2.
- **Auto-refresh hooks** (SessionStart, file watchers). v1 is manual via CLI.
- **Schema validation** of YAML configs. v1 fails loudly on missing required keys; full schema validation can wait.
- **Caching / incremental updates.** v1 does a fresh query every run.

## First consumer: job_search

YAML config lives at `~/projects/dev/job_search/dashboards/job_search.yaml`. Output is `~/projects/dev/job_search/DASHBOARD.md`. Sections per the sketch above; tag taxonomy per the sibling architecture mini-plan in job_search.

## Verification

1. **Smoke test against an empty notebook.** Create a temporary `_test_dashboard` notebook in Joplin, run the CLI with a minimal config pointing at it; expect a dashboard with empty section bodies and no errors.
2. **Smoke test against a populated notebook.** Add 2-3 test notes with the expected tags; rerun; verify rows render correctly with all configured columns.
3. **Group-by-phase test.** Tag two test notes with `Job: Phase 4`, one with `Job: Phase 5`, one with no phase tag; verify three groups (4, 5, none) emit in the rendered section.
4. **Tag-exclusion test.** Add `tags_excluded: [...]` to a section; verify excluded notes don't appear.
5. **Frontmatter column test.** Add a note with `---\norg: mgb\n---` body prefix; configure a column reading that field; verify the value renders.
6. **End-to-end against job_search.** After the architecture mini-plan migration, run the CLI against the real `dashboards/job_search.yaml`; verify the resulting `DASHBOARD.md` reflects all migrated entities correctly.

## Open decisions

- (a) ~~Backend~~ — **resolved by 2026-05-06 research:** REST for v1, pluggable Loader, SQLite for v1.5. Pending user confirmation.
- (b) **Library placement** within joplin-mcp: `src/joplin_mcp/dashboard/` (sub-module of the MCP package) vs `src/joplin_dashboard/` (sibling package in the same repo). Defer to inspection of the existing joplin-mcp src layout.
- (c) **Frontmatter library:** `python-frontmatter` (purpose-built) vs stdlib `yaml` with manual delimiter handling. Lean: `python-frontmatter`.
- (d) **CLI entry point** registration: pyproject.toml `[project.scripts]` entry, or a standalone script under `bin/`. Lean: `[project.scripts]` for installability.
- (e) **Test framework:** match joplin-mcp's existing test conventions (pytest, by file inspection). Verify on implementation.
